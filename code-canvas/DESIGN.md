# Code Canvas — 设计纪要 v0

> 推倒重来的新方向。取代 code-review-skill / code-reading-walkthrough 的
> "线性 HTML 长文档" 形态。本文档记录已收敛的设计决定和待定问题。

## 1. 问题诊断

旧项目本质上是"一本更好的书"：storyline → step → 大段 prose 字段，最终
仍是从上往下滚动的线性文档。文字量越大，单位信息的阅读成本越高。
方向性问题，打磨解决不了。

核心洞察：**视觉对空间结构的感知是并行的，读文字是串行的**。
位置、颜色、连线、包含关系不用"读"，一眼获得。

## 2. 方向反转（对 no-code 工具的批判性继承）

Blueprint / Node-RED 这类 node-and-wire 图：**写起来低效（图作为源码，
输入密度太低），读起来高效**。所以反转方向：

- no-code：图是源码，代码是生成物 → 失败
- 我们：**代码是源码，图是投影（view）** → 写读不对称，各取所长

## 3. 信息通道分配

| 信息类型 | 通道 |
|---|---|
| 拓扑（谁调用谁、数据流向、模块边界） | 空间布局 + 连线 |
| 变更 delta | 颜色（diff 着色） |
| 意图 / 不变量 / tradeoff | 短注释，贴在具体代码行边上 |
| 代码本身 | 原文保留，永远可见可展开 |

## 4. 粒度（与 no-code 的关键分歧）

- 节点 = **函数级代码卡片**，卡片内部是真实的、语法高亮的代码原文
- **函数内部 → 文本通道**：局部控制流（if/for/嵌套）代码本身表达最好，不画
- **函数之间 → 图通道**：跨函数调用与数据流，文本最弱、连线最强

绝不做 Blueprint 的表达式级粒度（一个加法一个节点 = 噪音炸弹）。

## 5. 两种线，严格分开（继承自 Blueprint）

- **调用/执行线**（灰白）：call site 那一行 → 被调函数卡片。便宜、可靠、默认画。
- **数据流线**（琥珀）：值从产生处流向消费处。贵（需真正理解代码），
  **介于主菜和配菜之间**：不全画，由 agent 在故事需要时选择性画几根关键的。

绝不把调用/依赖/数据流画成同一种箭头。

## 6. 分层细节（tiered detail）

- **重点函数**：展开态，有**行级端口**——连线精确锚到具体行；
  端口同时兼任 **note 的锚点**（行级短注释用引线贴在行边）
- **次要函数**：折叠成签名块
- **一切块都能点开看真码**：没有任何节点是"只有描述没有代码"的

## 7. 线是策展的，不是全量的

静态分析全量边 = 毛线球（Sourcetrail / CodeSee 的死法）。
线由 agent 作为叙事的一部分挑选。完备性由代码本身保证（它永远是真的），
图只负责"此刻你需要看见的关系"。

## 8. Storyline 的新形态

保留旧项目的叙事策展（这是死掉的可视化工具们缺的东西），但改变载体：

- storyline = 画布上一块**着色区域**（Blueprint comment box 的用法）
- step = **镜头路径 + 逐步点亮**：镜头移到当前卡片，本步相关的线实色，
  其余淡出；相关行高亮，相关 note 点亮
- 读者随时可以缩出去看全图（色块 = 章节地图），也可以顺故事一步步走

## 9. 语义缩放三层

1. 最远：storyline 色块 + 模块框
2. 中间：卡片只显示函数签名 + 端口
3. 贴近：完整代码原文 + 行注释

## 10. 待定问题

- [ ] 布局：agent 手工指定坐标 vs 自动布局（分层 DAG？）vs 混合（agent 给相对关系，渲染器排）
- [ ] diff 模式怎么叠加：卡片内 diff 着色 + "改动前后"的卡片对？先做 diff review 还是 code reading？
- [ ] JSON schema 设计（卡片 / 线 / 区域 / 步骤 / note）
- [ ] 渲染器：延续单文件 HTML 模板 + 注入 JSON 的架构？
- [ ] 大 storyline 的空间预算：一屏硬约束（邻域卡片 ≤3-4、行注释 ≤5）如何执行

## 现状

- `mock/canvas-mock-v1.html` — 手工排版的形态 mock：真代码卡片、两种线、
  行级端口 + note、折叠/展开、平移缩放、故事线区域 + 步进镜头。
  用于钉死视觉形态，不是生成器产物。
